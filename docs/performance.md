# ⚡ Performance & Stability

대용량 데이터를 다루는 BI 서비스에서 반복적으로 만났던 성능·안정성 문제와 해결 과정을 정리했습니다. 병목이 브라우저에 있으면 렌더링과 계산 횟수를, 서버·DB에 있으면 가공 위치·쿼리·커넥션을 고쳤습니다. 모든 항목은 **문제 → 원인 분석 → 해결 방법 → 결과** 순서로 정리했으며, 어떤 프로젝트에서 있었던 일인지 함께 표기했습니다.

기능을 먼저 완성한 뒤 실제로 느린 지점을 찾아 그 지점만 고치는 방식으로 작업합니다. 아래 사례는 모두 커밋 이력이나 소스에 남긴 변경 기록으로 확인되는 작업입니다.

## 1. SpreadJS 보고서 저장·불러오기·바인딩 개선

**관련 프로젝트**: [전사 관리 지표 플랫폼 (홈앤쇼핑)](./career.md) (2024.01 ~ 2025.05)

### 문제

엑셀 양식 그대로 보는 SpreadJS 보고서에서 파일 저장·불러오기와 데이터 바인딩이 오래 걸렸고, 바인딩 후 서식이 지워지거나 같은 보고서 파일이 여러 개 생기는 문제가 있었습니다. 틀 고정을 해제한 넓은 보고서는 스크롤 영역 전체를 한 번에 그리느라 로드가 느렸습니다.

### 원인 분석

- 조회 결과를 셀 단위로 시트에 써 넣고 있어, 데이터 양에 비례해 바인딩 시간이 늘어났습니다.
- `.sjs` 파일을 열 때 시트 전체를 즉시 로드하는 모드를 쓰고 있었습니다.
- 파일 저장·불러오기·삭제 로직이 흩어져 있어 파일명 중복·누락을 막는 지점이 없었습니다.

### 해결 방법

- 데이터 바인딩을 테이블 단위(tableBinding)로 바꾸고, 데이터가 없으면 바인딩 호출 자체를 생략
- 파일 열기 모드를 지연 로드(lazy)로 변경
- 틀 고정 해제 시 그리드 내부 스크롤(native scroll)을 쓰도록 바꿔 보이는 영역만 먼저 그리도록 조정
- 서버의 보고서 파일 저장·불러오기·삭제 로직을 정리하고, 엑셀 생성은 서버 dsExcel 처리로 전환

### 결과

- 스프레드 보고서 저장·불러오기·엑셀 다운로드 속도 개선
- 파일 중복 생성·서식 유실 문제 해소

## 2. 셀 단위 반복 계산 제거

**관련 프로젝트**: [WISEOLAP React·Spring Boot 전환](./career.md)

### 문제

데이터 그리드에서 측정값을 막대(bar)로 표시하는 열이 있으면, 행이 많아질수록 그리드 렌더링이 눈에 띄게 느려졌습니다.

### 원인 분석

- 막대 길이의 기준이 되는 열 최댓값을 **셀을 그릴 때마다** 전체 데이터에서 다시 계산하고 있었습니다. 행이 N개면 계산량이 N²으로 늘어나는 구조였습니다.

### 해결 방법

- 열별 최댓값을 한 번만 계산해 저장하고, 셀 렌더링에서는 저장된 값을 재사용하도록 변경

### 결과

- 최댓값 계산을 열당 1회로 줄여, 행 수가 늘어도 막대 표시 열의 렌더링 비용이 행 수에 비례하는 수준으로 감소

## 3. 불필요한 리렌더링 제거

**관련 프로젝트**: [전사 관리 지표 플랫폼 (홈앤쇼핑)](./career.md)

### 문제

환경설정의 수행 쿼리 정보 화면에서 그리드의 행 하나만 클릭해도 화면 전체가 다시 그려지며 반응이 느려졌습니다.

### 원인 분석

- 선택 상태를 가진 상위 컴포넌트 안에 그리드가 직접 정의되어 있어, 선택이 바뀔 때마다 그리드가 새로 만들어졌습니다.

### 해결 방법

- 그리드를 독립 컴포넌트로 분리해, 선택 변경이 그리드 재생성으로 이어지지 않도록 구조 변경
- 같은 원칙으로 탭 패널 렌더링을 최적화하고, 계산 비용이 큰 곳에만 `useMemo`·`useCallback` 적용

### 결과

- 행 클릭 시 화면 전체가 다시 그려지던 현상 제거

## 4. 지도 마커·오버레이 관리

**관련 프로젝트**: [WISEOLAP JSP 버전 고도화](./career.md) (문화정보원 카카오 지도 위젯, 2020.08 ~ 11)

### 문제

카카오 지도 위젯에서 마커가 수천 개 단위로 늘어나면 지도가 마커로 뒤덮여 읽을 수 없었고, 조회 조건을 바꿔 다시 그리거나 툴팁을 여러 번 열면 이전 마커·폴리곤·툴팁이 지도에 남아 겹쳐 보였습니다.

### 원인 분석

- 모든 데이터 포인트를 개별 마커로 그리고 있었습니다.
- 다시 그릴 때 새 오버레이만 추가하고, 이전에 만든 마커·폴리곤·툴팁(CustomOverlay)을 지도에서 떼어내지 않았습니다.

### 해결 방법

- 마커 클러스터러로 가까운 마커를 묶어 표시하고, 데이터 값 크기에 따라 표시할 마커를 거르는 범위 슬라이더 추가
- 다시 그리기 전에 이전 마커·폴리곤·CustomOverlay를 `setMap(null)`로 지도에서 해제
- 새 툴팁을 열 때 열려 있던 툴팁을 먼저 닫아 한 번에 하나만 열리도록 정리
- 타일셋은 한반도가 보이는 줌 레벨에서만 표시

### 결과

- 마커가 많아도 클러스터 단위로 읽을 수 있는 지도 제공
- 재조회·툴팁 조작 시 오버레이가 겹쳐 남던 현상 해소

## 5. Top/Bottom 서버 처리

**관련 프로젝트**: [WISEOLAP React·Spring Boot 전환](./career.md) (2024.01)

### 문제

상·하위 N개만 보여주는 Top/Bottom 기능을 화면에서 처리하면, 그리지도 않을 데이터까지 모두 내려받아 브라우저에서 정렬·절단해야 했습니다.

### 원인 분석

- Top/Bottom은 집계가 끝난 결과 위에서 동작해야 하는데, 집계 이후 단계가 서버에 없어 화면이 그 역할을 떠안는 구조였습니다.

### 해결 방법

- 서버 데이터 정제 파이프라인(`DataSanitizer`)에 Top/Bottom 단계를 추가하고, 유형·개수·기준 측정값을 담은 `TopBottomInfo`를 구현해 차트·피벗그리드 데이터 가공에 연결
- 화면에는 Top/Bottom 설정 모달·폼을 만들어 아이템별로 조건을 지정하도록 구성

### 결과

- 화면에는 이미 잘린 결과만 전달되도록 구조 개선
- 이후 동료가 차원 계층별 그룹 처리를 더한 구조(`TopBottomFilter`)로 확장해 홈앤쇼핑 운영에 사용

## 6. 공용 보고서 목록 조회 개선

**관련 프로젝트**: [전사 관리 지표 플랫폼 (홈앤쇼핑)](./career.md)

### 문제

보고서가 쌓이면서 환경설정의 공용 보고서 관리 화면을 여는 데 시간이 오래 걸렸습니다.

### 원인 분석

- 서버에서 보고서마다 폴더 목록 전체를 다시 순회해 소속 폴더를 확인하는 이중 반복문 구조였습니다(보고서 수 × 폴더 수).
- 같은 게시자의 사용자명을 보고서마다 반복해서 조회하고 있었습니다.

### 해결 방법

- 폴더 ID를 `Set`으로 만들어 소속 여부를 한 번에 확인하도록 변경
- 사용자명 조회 결과를 요청 범위 안에서 캐시해 중복 조회 제거

### 결과

- 보고서 수와 폴더 수를 곱한 만큼 늘던 비교 횟수를 둘을 더한 수준으로 줄여 목록 로딩 속도 개선

## 7. DB 커넥션 풀 고갈 해결

**관련 프로젝트**: [고객사 BI 구축](./career.md) (한국자활복지개발원, WISEOLAP 공공기관 공통 버전)

### 문제

포털에 연동된 BI에서 여러 사용자가 대용량 상세 데이터를 동시에 조회하면, 일정 시간 뒤 새 요청이 커넥션을 얻지 못하고 타임아웃되는 현상이 반복됐습니다.

### 원인 분석

- 기본값에 가까운 커넥션 풀 설정으로는 오래 걸리는 상세 데이터 쿼리가 커넥션을 점유하는 동안 다른 요청이 대기열에 쌓였습니다.
- 유휴 커넥션 수명과 검증 설정이 DB 측 세션 정책과 맞지 않아, 끊긴 커넥션을 재사용하다 실패하는 경우도 있었습니다.

### 해결 방법

- HikariCP 최대 풀 크기·최소 유휴 커넥션·idle-timeout·max-lifetime·connection-timeout을 고객사 DB 세션 정책에 맞춰 재설정하고, 커넥션 검증 쿼리 추가
- 공공기관 공통 버전에서는 Hikari 설정을 `@ConfigurationProperties`로 외부화해 기관별로 소스 수정 없이 조정 가능하게 구성

### 결과

- 대용량 상세 조회 시 반복되던 커넥션 고갈·타임아웃 해소
- 기관별 배포 시 설정 파일만으로 풀 정책 대응

## 8. 잘못된 GROUP BY로 인한 집계 오류 수정

**관련 프로젝트**: [고객사 BI 구축](./career.md) (한국자활복지개발원, WISEOLAP 공공기관 공통 버전)

### 문제

집계 없이 원본 값을 그대로 보여주도록 설정한(NOFUNC) 측정값으로 상세 데이터를 조회하면, 값이 합산되거나 쿼리에 존재하지 않는 함수명이 붙어 오류가 났습니다.

### 원인 분석

- 쿼리 생성기(QueryGen)가 측정값이 여러 개일 때 NOFUNC 측정값에도 일괄적으로 기본 집계(SUM)와 `GROUP BY`를 적용하고 있었습니다.
- 같은 계열의 문제로, 공공기관 공통 버전에서는 주제영역에서 이미 집계된 측정값에 `GROUP BY` + `COUNT`/`COUNT DISTINCT`가 한 번 더 적용되어 결과가 틀어지는 경우도 있었습니다.

### 해결 방법

- 선택된 측정값이 **모두** NOFUNC인지 먼저 판별해, 모두 NOFUNC이면 집계 함수와 `GROUP BY`를 생략
- NOFUNC와 일반 측정값이 섞인 경우에만 기본 집계를 적용하도록 분기 정리
- 보고서 자체 필터·매개변수가 상세 데이터 쿼리의 조건절에 함께 반영되도록 수정
- 공공기관 공통 버전의 이중 집계는 서버 데이터 정제 단계(`DataSanitizer`)에서 이미 집계된 측정값을 판별해 재집계하지 않도록 수정

### 결과

- 상세 데이터 조회 결과가 원본과 일치하도록 정합성 확보
- 쿼리 실행 오류 제거

## 9. 파일 다운로드 Path Traversal 조치

**관련 프로젝트**: [고객사 BI 구축](./career.md) (스포츠토토)

### 문제

외부 웹 취약점 점검에서 파일 다운로드 API의 Path Traversal 취약점이 지적됐습니다.

### 원인 분석

- 다운로드 요청의 파일명을 검증 없이 기준 폴더 경로와 이어 붙이고 있어, `../` 등을 넣으면 기준 폴더 밖 파일에 접근할 수 있었습니다.

### 해결 방법

- 파일명을 화이트리스트 정규식(`^[a-zA-Z0-9._-]+$`)으로 1차 검증
- 기준 폴더와 대상 파일의 Canonical Path를 구해, 대상이 기준 폴더 하위가 아니면 `SecurityException`으로 차단

### 결과

- 외부 보안 점검에서 지적된 다운로드 취약점 조치 완료

## 10. 요청 본문 암호화로 SQL Injection 차단

**관련 프로젝트**: [고객사 BI 구축](./career.md) (스포츠토토)

### 문제

같은 점검에서, 보고서 조회 요청을 프록시 도구로 가로채 조회 조건 값을 바꾸면 SQL이 주입될 수 있다는 취약점이 지적됐습니다.

### 원인 분석

- BI 조회 요청에는 필터·매개변수 등 쿼리 생성에 쓰이는 값이 JSON 평문으로 담겨 있어, 브라우저와 서버 사이에서 변조가 가능했습니다.
- 쿼리 생성 로직이 수많은 API에서 공유되고 있어, API마다 개별 검증을 덧붙이는 방식은 누락 위험이 컸습니다.

### 해결 방법

- **Frontend**: axios 요청 인터셉터에서 요청 본문을 AES-256(CBC)으로 암호화해 전송
- **Backend**: Spring `RequestBodyAdvice`에서 모든 `@RequestBody`를 가로채, JWT로 식별한 세션별 키로 복호화한 뒤에만 컨트롤러에 전달 (로그인 요청은 예외 처리)
- 암호화·복호화를 요청 경계 한곳에서 처리해 기존 컨트롤러·쿼리 생성 코드는 수정하지 않음

### 결과

- 요청 변조를 통한 SQL Injection 경로 차단, 재점검 조치 완료
- 이후 추가되는 API에도 별도 작업 없이 동일하게 적용
