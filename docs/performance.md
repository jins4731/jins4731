# ⚡ Performance & Stability

대용량 데이터를 다루는 BI 서비스에서 만났던 성능·안정성 문제와 해결 과정입니다.

병목이 어디 있는지부터 확인하고, 그 위치에 맞는 방법을 골랐습니다.
- **브라우저**가 병목이면 렌더링 범위와 계산 횟수를 줄였습니다.
- **서버·DB**가 병목이면 가공 위치, 쿼리, 커넥션 설정을 고쳤습니다.
- **구조적인 보안 문제**는 API마다 고치지 않고 요청이 들어오는 한 곳에서 막았습니다.

각 사례는 **문제 → 원인 → 해결 → 왜 이 방법인가 → 결과** 순서입니다. 회사 소스는 공개할 수 없어 코드는 구조를 설명하는 예시로만 넣었습니다.

# Frontend

## 1. 대시보드 아이템별 로딩

**관련 프로젝트**: [WISEOLAP React·Spring Boot 버전](./career.md) (대시보드·비정형 보고서)

### 문제
대시보드를 열면 **모든 아이템이 다 그려질 때까지 전체 화면이 로딩 상태**였습니다. 아이템 하나만 느려도 나머지 아이템까지 함께 기다려야 했습니다.

### 원인
- 로딩 상태를 화면 전체에 하나만 두고 있어, 아이템 중 가장 느린 것이 화면 전체의 표시 시점을 결정했습니다.
- 아이템 컴포넌트 안에 데이터 처리와 화면 표시가 섞여 있어, 로딩 경계를 아이템 단위로 나누기 어려웠습니다.

### 해결
1. 아이템 렌더링을 **Container/Presentational**로 전면 개편해, 데이터를 준비하는 부분과 그리는 부분을 나눴습니다.
2. 나뉜 아이템마다 **`Suspense` 경계**를 두어, 아이템별로 로딩을 표시하도록 바꿨습니다.

```jsx
// 구조 예시
{items.map((item) => (
  <Suspense key={item.id} fallback={<ItemLoading />}>
    <ItemContainer item={item} />   {/* 데이터 준비 */}
  </Suspense>
))}
// ItemContainer → ChartView / GridView (화면 표시만 담당)
```

### 왜 이 방법인가
로딩을 빠르게 하는 것보다 **기다리는 범위를 줄이는 것**이 먼저였습니다. 아이템마다 데이터 양과 쿼리가 달라 모두를 같은 속도로 만들 수는 없지만, 느린 아이템이 다른 아이템을 막지 않게 할 수는 있었습니다.

### 결과
- 준비된 아이템부터 바로 표시되어, 사용자가 느린 아이템을 기다리는 동안 다른 아이템을 먼저 볼 수 있게 됐습니다.
- 데이터 처리와 화면이 분리되어 아이템별 유지보수가 쉬워졌습니다.

## 2. 불필요한 재렌더링 제거

**관련 프로젝트**: [전사 관리 지표 플랫폼 (홈앤쇼핑)](./career.md)

### 문제
환경설정의 쿼리 실행 정보 화면에서 그리드의 **행 하나만 클릭해도 화면 전체가 다시 그려져** 반응이 느렸습니다.

### 원인
- 선택 상태를 가진 상위 컴포넌트 안에 그리드가 직접 정의되어 있었습니다.
- 그래서 선택이 바뀔 때마다 그리드 컴포넌트가 **새로 만들어져**, 수천 행을 처음부터 다시 그렸습니다.

```jsx
// Before: 상위 컴포넌트가 렌더링될 때마다 Grid가 새 컴포넌트로 만들어짐
function QueryLogPage() {
  const [selected, setSelected] = useState();
  const Grid = () => <DataGrid dataSource={logs} onRowClick={...} />;
  return <><Grid /><Detail row={selected} /></>;
}

// After: 그리드를 밖으로 분리하고, props가 같으면 다시 그리지 않음
const QueryLogDataGrid = React.memo(({ logs, onRowClick }) => (
  <DataGrid dataSource={logs} onRowClick={onRowClick} />
));
```

### 해결
- 그리드를 독립된 표현 컴포넌트로 분리하고 `React.memo`로 감쌌습니다.
- 그리드에 넘기는 콜백은 `useCallback`으로 고정해, 선택이 바뀌어도 그리드의 props가 바뀌지 않게 했습니다.
- Redux에서 여러 상태를 조합하는 곳은 reselect `createSelector`를 써서, 원본 상태가 그대로면 이전 결과(같은 참조)를 돌려주게 했습니다.
- 같은 원칙으로 탭 패널 렌더링도 정리했습니다.

### 왜 이 방법인가
`useMemo`와 `useCallback`을 모든 곳에 넣는 대신, **다시 그릴 필요가 없는 큰 컴포넌트를 먼저 분리**했습니다. 컴포넌트가 매번 새로 만들어지는 구조에서는 메모이제이션을 해도 효과가 없기 때문입니다.

### 결과
- 행을 클릭하면 상세 영역만 다시 그려지고, 그리드는 그대로 유지됩니다.

## 3. 셀 단위 반복 계산 제거

**관련 프로젝트**: [WISEOLAP React·Spring Boot 버전](./career.md)

### 문제
데이터 그리드에서 측정값을 막대(bar)로 표시하는 열이 있으면, **행이 많아질수록 렌더링이 눈에 띄게 느려졌습니다.**

### 원인
막대 길이의 기준인 열 최댓값을 **셀을 그릴 때마다 전체 데이터에서 다시 계산**하고 있었습니다. 행이 N개면 N번 그리면서 매번 N개를 훑으므로 계산량이 N²이었습니다.

```js
// Before: 셀마다 전체 행을 훑음 → O(N²)
cellRender = (cell) => {
  const max = Math.max(...rows.map((r) => r[cell.column]));
  return <Bar ratio={cell.value / max} />;
};

// After: 열별 최댓값을 한 번만 계산해 재사용 → O(N)
const maxByColumn = useMemo(() => computeMaxByColumn(rows, barColumns), [rows, barColumns]);
cellRender = (cell) => <Bar ratio={cell.value / maxByColumn[cell.column]} />;
```

### 해결
열별 최댓값을 데이터가 바뀔 때 한 번만 계산해 두고, 셀을 그릴 때는 저장된 값만 읽도록 바꿨습니다.

### 결과
- 최댓값 계산이 열당 1회로 줄어, 렌더링 비용이 행 수의 제곱이 아니라 행 수에 비례하게 됐습니다.

## 4. 대용량 엑셀 다운로드 서버 전환

**관련 프로젝트**: [전사 관리 지표 플랫폼 (홈앤쇼핑)](./career.md) (2024.08 ~ 2025.05)

### 문제
홈앤쇼핑은 설치형(CS) BI에서 웹 BI로 옮기면서, 엑셀 자리를 SpreadJS가 대신하게 됐습니다. 현업은 여전히 사내 엑셀에서 작업했기 때문에 데이터를 엑셀로 옮겨야 했는데, 두 방법 모두 문제가 있었습니다.
- **복사·붙여넣기**: 서식이나 수식이 있는 셀은 매우 오래 걸렸습니다.
- **다운로드**: 숫자 서식이 '일반'으로 바뀌고, 4만 행이 넘으면 형식이 깨졌습니다. 큰 보고서는 아예 다운로드에 실패했습니다.

### 원인
- 복사는 셀마다 서식·수식 정보를 클립보드로 넘기는 구조라, 제품 코드로 속도를 올리는 데 한계가 있었습니다.
- 다운로드는 **엑셀 파일을 브라우저에서 생성**하고 있어, 큰 보고서에서는 브라우저가 과부하로 멈췄습니다.

### 해결
1. **방향 정하기**: 라이브러리 제조사와 회의해 클립보드 한계를 확인했습니다. 적은 양은 복사로, 많은 양이나 서식이 필요한 경우는 다운로드로 나누고, 다운로드는 **서버에서 생성**하기로 했습니다.
2. **1차 구현과 실패**: 보고서를 JSON 문자열로 바꿔 서버로 보냈습니다. 그런데 데이터가 크면 JSON 문자열 자체가 너무 커져 전송되지 않았고, 운영에 영향이 없도록 바로 기존 방식으로 되돌렸습니다.
3. **원인을 고쳐 재시도**: JSON 대신 SpreadJS 전용 파일(`.sjs`)로 보내고, 서버가 **스트림으로 받아 xlsx로 변환**하도록 다시 만들었습니다. 받은 파일을 열 때 뜨던 "통합 문서 복구" 경고는 재현 파일을 제조사에 보내 원인을 확인하고, 안내받은 버전으로 라이브러리를 업데이트했습니다.
4. **받은 파일을 바로 쓸 수 있게**: 날짜를 문자열이 아닌 SpreadJS 날짜 서식으로 바꿔, 엑셀 날짜 함수가 바로 동작하게 했습니다.

```
Before  브라우저: 시트 → xlsx 생성 (대용량에서 멈춤)
1차     브라우저: 시트 → JSON 문자열 ──▶ 서버: JSON → xlsx   (문자열이 너무 커서 실패)
2차     브라우저: 시트 → .sjs 파일 ──▶ 서버: 스트림 읽기 → xlsx → 다운로드
```

### 왜 이 방법인가
- 복사 속도는 클립보드 구조 때문에 한계가 분명했고, 현업이 실제로 원한 것은 **서식이 살아 있는 엑셀 파일**이었습니다.
- 파일 생성을 서버로 옮기면 사용자 PC 성능이나 엑셀 버전과 상관없이 같은 파일을 받을 수 있습니다.

### 결과

| 항목 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 서식 있는 셀 복사 | 매우 느림 | 서식 복사를 꺼서 빠르게 (적은 양) |
| 서식 유지 | 다운로드하면 숫자 서식이 '일반'으로 바뀜 | 서버 다운로드로 서식 유지 |
| 대용량 보고서 | 브라우저 과부하로 다운로드 실패 | 서버에서 생성해 정상 다운로드 |
| 날짜 데이터 | 문자로 저장되어 엑셀 함수 사용 불가 | 날짜 형식이라 함수 바로 사용 |

- 현업이 받은 파일을 따로 정리하지 않고 바로 엑셀에서 작업할 수 있게 되어, 웹 전환으로 끊겼던 엑셀 업무 흐름이 다시 이어졌습니다.

## 5. SpreadJS 저장·불러오기·바인딩

**관련 프로젝트**: [전사 관리 지표 플랫폼 (홈앤쇼핑)](./career.md) (2024.04 ~ 2024.11)

### 문제
- SpreadJS 보고서의 데이터 바인딩과 파일 저장·불러오기가 오래 걸렸습니다.
- 바인딩 후 서식이 지워지거나, 같은 보고서 파일이 여러 개 생기는 문제가 있었습니다.
- 틀 고정을 해제한 넓은 보고서는 처음 열 때 오래 걸렸습니다.

### 원인
- 조회 결과를 **셀 단위로 하나씩** 시트에 써 넣고 있어, 데이터 양에 비례해 바인딩 시간이 늘었습니다.
- 파일을 열 때 시트 전체를 즉시 불러오는 모드를 쓰고 있었습니다.
- 파일 저장·불러오기·삭제 로직이 흩어져 있어, 파일명 중복을 막는 지점이 없었습니다.

### 해결
- 셀 단위 쓰기를 **테이블 단위 바인딩**(tableBinding)으로 바꾸고, 데이터가 없으면 바인딩 호출을 생략했습니다.
- 저장 형식을 xlsx에서 SpreadJS 전용 형식(`.sjs`)으로 바꾸고, 파일을 **지연 로드** 모드로 열게 했습니다.
- 틀 고정 해제 시 보이는 영역부터 그리도록 스크롤 방식을 조정했습니다.
- 수식 계산 중에는 진행 표시를 띄워, 화면이 멈춘 것처럼 보이지 않게 했습니다.
- 파일 저장·불러오기·삭제 로직을 한 곳으로 정리했습니다.

### 결과
- 바인딩·저장·불러오기 시간이 줄고, 파일 중복 생성과 서식 유실이 사라졌습니다.

## 6. 지도 마커·오버레이 관리

**관련 프로젝트**: [WISEOLAP JSP 버전](./career.md) (카카오 지도 위젯, 2020.08 ~ 11)

### 문제
- 마커가 수천 개로 늘면 지도가 마커로 뒤덮여 읽을 수 없었습니다.
- 조회 조건을 바꿔 다시 그리면 **이전 마커·폴리곤·툴팁이 지도에 남아** 겹쳐 보였습니다.

### 원인
- 모든 데이터를 개별 마커로 그리고 있었습니다.
- 다시 그릴 때 새 오버레이만 추가하고, 이전 오버레이를 지도에서 떼어 내지 않았습니다. 화면에 안 보여도 지도 객체에는 계속 쌓이는 구조였습니다.

### 해결
- **마커 클러스터러**로 가까운 마커를 묶고, 값 범위 슬라이더로 표시할 마커를 거를 수 있게 했습니다.
- 다시 그리기 전에 이전 마커·폴리곤·툴팁을 `setMap(null)`로 해제했습니다.
- 툴팁은 새로 열 때 기존 툴팁을 먼저 닫아 하나만 열리게 했습니다.

### 결과
- 마커가 많아도 클러스터 단위로 읽을 수 있고, 재조회해도 오버레이가 쌓이지 않습니다.

## 7. Top/Bottom 서버 처리

**관련 프로젝트**: [WISEOLAP React·Spring Boot 버전](./career.md) (2024.01)

### 문제
상위·하위 N개만 보여 주는 Top/Bottom 기능을 화면에서 처리하면, **그리지도 않을 데이터까지 모두 내려받아** 브라우저에서 정렬하고 잘라야 했습니다.

### 원인
Top/Bottom은 집계가 끝난 결과 위에서 동작해야 하는데, 서버에 집계 이후 단계가 없어 화면이 그 역할을 떠안고 있었습니다.

### 해결
- 서버의 데이터 정제 단계에 Top/Bottom 단계를 추가하고, 유형·개수·기준 측정값을 담는 설정 객체를 만들어 차트·피벗 그리드 가공에 연결했습니다.
- 화면에는 아이템별로 조건을 지정하는 설정 창을 만들었습니다.

### 왜 이 방법인가
데이터를 줄이는 작업은 데이터가 있는 곳에서 해야 전송량과 브라우저 부담이 함께 줄어듭니다.

### 결과
- 화면에는 이미 잘린 N개만 전달됩니다.
- 이후 동료가 차원 계층별 처리를 더해 확장했고, 홈앤쇼핑 운영에 사용됐습니다.

## 8. 공용 보고서 목록 조회

**관련 프로젝트**: [전사 관리 지표 플랫폼 (홈앤쇼핑)](./career.md)

### 문제
보고서가 쌓이면서 공용 보고서 관리 화면이 열리는 데 오래 걸렸습니다.

### 원인
- 보고서마다 폴더 목록 전체를 다시 훑어 소속 폴더를 확인하는 **이중 반복문**이었습니다. (보고서 수 × 폴더 수)
- 같은 게시자의 사용자명을 보고서마다 다시 조회했습니다.

```java
// Before: 보고서 × 폴더
for (Report r : reports)
  for (Folder f : folders)
    if (f.getId() == r.getFolderId()) ...

// After: 폴더 ID를 Set으로 한 번 만들고 바로 확인
Set<Integer> folderIds = folders.stream().map(Folder::getId).collect(toSet());
for (Report r : reports)
  if (folderIds.contains(r.getFolderId())) ...
```

### 해결
- 폴더 ID를 `Set`으로 만들어 소속 여부를 바로 확인하게 했습니다.
- 사용자명 조회 결과를 요청 안에서 캐시해 중복 조회를 없앴습니다.

### 결과
- 비교 횟수가 보고서 수 × 폴더 수에서 보고서 수 + 폴더 수 수준으로 줄었습니다.

## 9. DB 커넥션 풀 고갈

**관련 프로젝트**: [고객사 BI 구축](./career.md) (한국자활복지개발원, 공공기관 공통 버전)

### 문제
포털에 연동된 BI에서 여러 사용자가 대용량 상세 데이터를 동시에 조회하면, 일정 시간 뒤 **새 요청이 커넥션을 얻지 못하고 타임아웃**되는 현상이 반복됐습니다.

### 원인
- 기본값에 가까운 풀 설정에서, 오래 걸리는 상세 쿼리가 커넥션을 붙잡고 있는 동안 다른 요청이 대기열에 쌓였습니다.
- 유휴 커넥션 수명이 DB의 세션 정책보다 길어, **DB가 이미 끊은 커넥션을 재사용**하다 실패하는 경우도 있었습니다.

### 해결
- HikariCP의 최대 풀 크기, 최소 유휴 수, idle-timeout, max-lifetime, connection-timeout을 고객사 DB 세션 정책에 맞춰 다시 설정하고, 커넥션 검증 쿼리를 추가했습니다.
- 공공기관 공통 버전에서는 풀 설정을 `@ConfigurationProperties`로 외부화해, 기관마다 소스 수정 없이 설정 파일로 조정하게 했습니다.

### 왜 이 방법인가
풀 크기만 늘리면 DB에 부담이 옮겨 갈 뿐이고, 끊긴 커넥션 문제는 그대로 남습니다. 그래서 **커넥션 수명을 DB 정책보다 짧게** 맞추는 것과 풀 크기 조정을 함께 했습니다.

### 결과
- 대용량 상세 조회 시 반복되던 커넥션 고갈과 타임아웃이 사라졌습니다.
- 기관별 배포 때 설정 파일만으로 대응할 수 있게 됐습니다.

## 10. GROUP BY 집계 오류

**관련 프로젝트**: [고객사 BI 구축](./career.md) (한국자활복지개발원, 공공기관 공통 버전)

### 문제
집계 없이 원본 값을 그대로 보여 주도록 설정한(NOFUNC) 측정값으로 상세 데이터를 조회하면, **값이 합산되거나** 쿼리에 없는 함수명이 붙어 오류가 났습니다.

### 원인
- 쿼리 생성기가 측정값이 여러 개일 때 NOFUNC 측정값에도 일괄적으로 SUM과 `GROUP BY`를 붙이고 있었습니다.
- 같은 계열로, 이미 집계된 측정값에 `COUNT`가 한 번 더 적용되는 **이중 집계**도 있었습니다.

### 해결
- 선택한 측정값이 **모두** NOFUNC이면 집계 함수와 `GROUP BY`를 생략하고, 섞여 있을 때만 기본 집계를 적용하도록 분기를 정리했습니다.
- 보고서 필터와 매개변수가 상세 데이터 쿼리 조건에도 반영되게 했습니다.
- 이중 집계는 서버 데이터 정제 단계에서 이미 집계된 측정값을 판별해 다시 집계하지 않게 했습니다.

### 결과
- 상세 데이터 조회 결과가 원본과 일치하고, 쿼리 실행 오류가 사라졌습니다.

## 11. 파일 다운로드 Path Traversal

**관련 프로젝트**: [고객사 BI 구축](./career.md) (스포츠토토)

### 문제
외부 보안 점검에서 파일 다운로드 API의 Path Traversal 취약점이 지적됐습니다.

### 원인
요청받은 파일명을 검증 없이 기준 폴더 경로에 이어 붙이고 있어, `../`를 넣으면 **기준 폴더 밖 파일에 접근**할 수 있었습니다.

### 해결
두 단계로 막았습니다.
1. 파일명을 화이트리스트 정규식(`^[a-zA-Z0-9._-]+$`)으로 먼저 검증합니다.
2. 기준 폴더와 대상 파일의 **실제 경로(Canonical Path)**를 구해, 대상이 기준 폴더 아래가 아니면 차단합니다.

### 왜 이 방법인가
정규식만으로는 인코딩을 바꾼 우회 입력을 놓칠 수 있습니다. 실제 경로를 비교하면 입력이 어떤 형태든 **최종적으로 어디를 가리키는지**로 판단할 수 있습니다.

### 결과
- 점검에서 지적된 다운로드 취약점 조치를 마쳤습니다.

## 12. 요청 본문 암호화

**관련 프로젝트**: [고객사 BI 구축](./career.md) (스포츠토토)

### 문제
같은 점검에서, 보고서 조회 요청을 프록시 도구로 가로채 조회 조건을 바꾸면 **SQL이 주입될 수 있다**는 취약점이 지적됐습니다.

### 원인
- BI 조회 요청에는 쿼리 생성에 쓰이는 필터·매개변수가 JSON 평문으로 담겨 있어, 중간에서 바꿀 수 있었습니다.
- 쿼리 생성 로직을 수많은 API가 공유하고 있어, API마다 검증을 붙이면 빠뜨릴 위험이 컸습니다.

### 해결
요청이 오가는 **양 끝 한 곳씩**에서만 처리했습니다.

```
브라우저                                      서버
axios 요청 인터셉터                            RequestBodyAdvice
  요청 본문 → AES-256 암호화  ───────────▶     JWT로 세션 키 확인 → 복호화 → 컨트롤러
```

- **Frontend**: axios 요청 인터셉터에서 모든 요청 본문을 AES-256으로 암호화해 보냅니다.
- **Backend**: Spring `RequestBodyAdvice`가 모든 `@RequestBody`를 가로채, 세션별 키로 복호화한 뒤에만 컨트롤러에 넘깁니다. 로그인 요청은 예외로 처리했습니다.

### 왜 이 방법인가
API마다 고치는 방식은 지금 있는 API는 막아도 **앞으로 추가될 API**에서 빠뜨리기 쉽습니다. 요청 경계에서 처리하면 기존 컨트롤러와 쿼리 생성 코드를 건드리지 않고, 새 API에도 자동으로 적용됩니다.

### 결과
- 요청 변조를 통한 SQL Injection 경로를 막고, 재점검을 통과했습니다.
- 이후 추가된 API에도 별도 작업 없이 같은 보호가 적용됩니다.
